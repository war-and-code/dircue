# Deterministic scale and history tests

This suite complements the real Java and .NET repositories in `tests/performance`. It tests large checkout sizes, large individual files, project-manifest shapes, and packed Git history against the actual pinned Ruby Linguist 9.7.0 CLI. It never compiles jobs, invokes MSBuild, restores packages, runs repository scripts, or connects to external services.

The fixtures are synthetic and have not been validated as importable Talend projects. They contain no actual Talend exports or MOVEit samples. Format and layout choices follow these parts of the official Talend documentation:

- [CI checkout artifacts](https://help.qlik.com/talend/r/en-US/Cloud/software-dev-lifecycle-best-practices-guide/implementation-in-your-environment): `.item`, `.properties`, and Maven `pom.xml` generated by Talend CommandLine.
- [Building Jobs](https://help.qlik.com/talend/en-US/studio-user-guide/8.0-R2024-11/building-jobs?ver=28): exported job items, generated Java sources, launch scripts, and contexts.
- [Talend Data Catalog import layout](https://help.qlik.com/talend/en-US/talend-data-catalog/8.1/Content/Bridges/MIRTalendImport.htm): `process`, `metadata`, and `joblet` folders, plus external context files.
- [Java template files](https://help.qlik.com/talend/en-US/what-is-a-component/8.0/java-template-file): `.javajet` templates generate Java code.
- [Java debug mode](https://help.qlik.com/talend/en-US/debug-jobs/8.0/java-debug-mode): jobs expose generated Java code.

The XML uses a synthetic envelope and deterministic parameter records, rather than Talend's serialization schema. Asset files contain binary payloads with recognizable headers; they are not valid images. Record values vary to avoid measuring the compression of all-zero files. These choices do not reproduce the compressibility, framework mix, or history of an organization's projects.

## Workloads

| Scenario | Acceptance size and shape | Assertions |
| --- | --- | --- |
| `talend` | 2 GiB plus small root files; 2,048 jobs, 8,293 files, XML `.item`/`.properties`, contexts, generated Java, assets, Maven, template and launch script | Same language totals/file sets in Git and flat modes; generated Java excluded and then explicitly included (768 MiB of Java); Maven hook and `analyze all` language equivalence |
| `xml-log` | One fully written XML log of 1,153,433,601 bytes (1,100 MiB + 1) | Default data-language exclusion, then `linguist-detectable=true` inclusion; complete file byte accounting |
| `talend-packed` / `xml-log-packed` | The same checkout and attribute variants, stored as standalone Git packs without deltas | Packed-object correctness and RSS, independent of loose-object behavior |
| `dotnet-graph` | 2,048 SDK `.csproj` manifests, broad directory fan-out, nested directory paths up to 24 levels, long reference chains plus a cycle, central props and SDK settings | C# and NuGet observations, Git/flat equivalence; manifest graph is input only, not a tested build |
| `dotnet-graph` history | 64 intermediate edits of a 2 MiB C# file, followed by restoration of the identical final tree; Git repacked with delta compression | Report actual delta count/depth, pack hashes/sizes, total Git storage, and identical initial/final tree IDs |
| `boundaries` | Empty and one-byte files; 128 KiB − 1 / exact / + 1; 1 MiB − 1 / exact / + 1 | Prefix boundaries preserve full-size accounting and oracle exclusions |
| `tree-count` | Exactly 100,000 nested source files; default limit plus limits 99,999 / 100,000 / 100,001 | At-or-over-limit empty result and immediately-above-limit complete result, matching Ruby |

`--profile smoke` generates a few megabytes with the same control paths. Only `--profile acceptance` creates the GiB-scale workloads. `--scenario NAME` is repeatable on both scripts.

Files are written sequentially; the generator never seeks, truncates, or creates sparse padding. It records SHA-256, Git blob IDs, logical bytes, allocated blocks, Git storage, and unique allocated bytes. Git-free views hardlink identical payload inodes and copy attribute files independently. This saves duplicate storage while still presenting an actual directory without `.git`; per-view allocations double-count hardlinks, so use the unique allocation field for disk budgeting. Unique allocation counts file blocks; directory and filesystem metadata are included in the separately reported disk-free-space delta. Source size and `.git` history size are separate measurements. Both Talend variants share the same fully written payload files; changing the generated-code attribute adds only a small Git commit and another hardlinked flat view. The source checkout is approximately 2 GiB in the Talend case; it does not assume that a real 2 GiB directory contains 2 GiB of source rather than history.

Before comparison, the runner reads and hashes every unique flat payload and verifies the corresponding committed blob IDs. Both tools then run on the same filesystem with network access disabled. This verifies the fixture bytes before profiling. The profilers may read only prefixes, so logical source bytes per second cannot measure physical disk throughput.

## Reproduce

Use an otherwise idle Docker engine for timing. Allow less than 15 GiB of free disk budget for the suite; the generator conservatively checks available space and refuses to overwrite existing fixtures. The default profile is small. Use a new output path or explicitly remove your disposable volume before regeneration.

From the repository root, build the pinned reference image and matching Linux release binary as described in `tests/performance/README.md`, then:

```sh
mkdir -p .cache/stress-results
docker volume create dircue-stress-v1
python3 tests/performance/receipt.py --candidate bin/dircue-linux-arm64 \
  --output .cache/stress-results/build-receipt.json

docker run --rm --network none \
  -v dircue-stress-v1:/stress \
  -v "$PWD/tests/stress:/harness:ro" \
  dircue-linguist:9.7.0 \
  python3 /harness/generate.py --output /stress/acceptance --profile acceptance

# Add packed backends without duplicating checkout payloads.
docker run --rm --network none \
  -v dircue-stress-v1:/stress \
  -v "$PWD/tests/stress:/harness:ro" \
  dircue-linguist:9.7.0 \
  python3 /harness/pack_views.py --fixtures /stress/acceptance

docker run --rm --network none \
  -v dircue-stress-v1:/stress:ro \
  -v "$PWD/tests/stress:/harness:ro" \
  -v "$PWD/bin/dircue-linux-arm64:/candidate/dircue:ro" \
  -v "$PWD/.cache/stress-results:/results" \
  dircue-linguist:9.7.0 \
  python3 /harness/compare.py --fixtures /stress/acceptance \
    --output /results/acceptance.json --build-receipt /results/build-receipt.json \
    --runs 20 --warmup 3
```

Use `--runs 0` for correctness and single-run diagnostic wall/RSS measurements. These are not stable performance estimates. A timed run requires exact language names, percentage strings, complete byte totals and file sets against Ruby before measuring each case. Any mismatch, subprocess failure or timeout fails the report. The timer kills the entire process group on timeout. A slower Git candidate median fails timed acceptance. Flat timings are reported separately because Ruby does not natively offer the same Git-free source mode.

Each timing case records 20 runs after three warmups, rotates tool order, and retains wall time, user/system CPU time, and Linux peak RSS. GNU `/usr/bin/time` measures the target child from its small launcher; using the Python harness child directly would inherit Python's pre-exec fork high-water mark and inflate small-tool RSS. Wall time includes the same GNU time launcher overhead for each tool. p95 is an observed order statistic; these sample sizes cannot establish rare tails. Caches are warm after explicit warmups, and prior full fixture hash verification also warms storage. Keep timing runs free from other tests, corpus copies, builds and interactive workloads. Read `finished_at_utc`, `passed`, and `performance_passed` before considering a report complete.

Raw stdout/stderr/status and hashes are saved beside the JSON report. The report pins candidate bytes, generator/harness bytes, fixture manifest hash, Git revisions, reference version and environment; an optional build receipt is validated against the candidate SHA. Preserve the manifest as well:

```sh
docker run --rm --network none -v dircue-stress-v1:/stress:ro \
  dircue-linguist:9.7.0 cat /stress/acceptance/manifest.json \
  > .cache/stress-results/fixture-manifest.json
```

Results apply to these generated inputs and this environment. The public corpus uses shallow history; the synthetic packed-history variant separately tests the specific history described above. Neither covers all Talend, Java, .NET or XML repositories.

Record completed acceptance evidence with:

```sh
python3 tests/stress/record.py --report .cache/stress-results/acceptance.json \
  --fixture-manifest .cache/stress-results/fixture-manifest.json
```

The recorder requires all fourteen acceptance cases, a matching embedded build receipt, at least 20 runs and three warmups, finite positive timings/RSS, independently recomputed medians, identical retained reference/candidate outputs, and candidate Git medians at least as fast as Ruby. It refuses partial reports, missing artifacts, changed artifact hashes and slower cases.
