# 0.8.0 candidate validation

The candidate adds environment observations, inert saved-report planning, and comparison of focused/source-availability reports. It is prepared for independent review, not released. The implementation remains on a separate branch with development version `0.8.0-dev`; the measured binary uses the test label `0.8.0-rc.1`.

## Original candidate: source and artifacts

The optimized native macOS ARM64 candidate was built with Go 1.26.6 from clean commit `6922d1d3bb1e8bbffae8392144cd6f519710ce98`. Its SHA-256 is `8de7bdcd5881a98dbfdcadd567480989faa64739128f7609a304e588000c66f1`.

The baseline is the actual 0.7.0 release binary, SHA-256 `7bbc81abfc2d9abec4a997c21933492d39959f444560a6d6d631121f499933ad`. The inherited structural cases use the verified release worker, SHA-256 `73cc5ed95a5b81dcc97c91d57b99a0db4e71ff45bdb74ce8a8193e60e3d53740`.

[Retained receipts](../../tests/context_v080/results/) bind the binaries, compilation inputs, harnesses, fixture bytes, raw compatibility captures and performance samples. The receipt-integrity verifier compares stored raw captures and recomputes recorded sample summaries and checks current Go compilation inputs against the build manifest. Subsequent evidence/documentation commits do not change those compilation inputs. Checksums detect changes; they are not signed attestations.

## Correctness and compatibility

- All **278 inherited cases** matched raw stdout, stderr and exit status against 0.7.0. Coverage includes legacy language commands, projects, structural validation/native execution, 0.4 modules, and declarations/comparison.
- All **18 targeted cases** matched the released focus, availability and explanation commands, including an explicit failure case for each authored project fixture.
- The packaged context smoke passed **13 defined checks**: opt-in defaults, environment facts and worker-count determinism, capabilities, planning after source deletion, input identity and inert commands, focused/availability comparison, malformed input and request caps.
- `go vet ./...` and `go test -race ./...` passed. Maintained Enry tests and the selected Go Git race suites passed. Packaging contracts ran 73 tests successfully with two platform/opt-in skips; four context-receipt tests and twelve CI concurrency tests passed.
- Adversarial tests cover nonregular configuration barriers, dirty checkout versus selected Git tree, bounded/cached reads, malformed and duplicate JSON members, null and wrong-case SDK inputs, numeric constraint overflow, forged scope IDs, inconsistent source identities, partial coverage, differing counting policies, and unrequested planner inputs.

The new native context gate is wired into all five worker/release platforms. Pull-request CI supplies the cross-platform results after the PR opens; local evidence alone does not establish those results. No 0.8 release workflow, tag or publication has run.

## Measured cost

Measurements used one warmup and five samples per lane, reversing lane order on alternating repetitions. No intentional builds, tests or other benchmarks ran concurrently; ordinary desktop services remained active. Tables show medians. Fixture creation and content hashing were outside timing. All source content was hashed before and after measurement.

| Language-only workload | 0.7.0 wall | Candidate wall | 0.7.0 peak RSS | Candidate peak RSS |
| --- | ---: | ---: | ---: | ---: |
| ASP.NET Core: 16,515 files, 173,287,602 bytes | 1,247 ms | 1,232 ms | 63.28 MiB | 64.86 MiB |
| XML plus tiny project: 2,050 files, 2,147,483,778 bytes | 2,070 ms | 2,142 ms | 51.62 MiB | 51.67 MiB |

Language output was byte-identical on both workloads. The candidate median was about 1.2% lower on ASP.NET Core and **3.5% higher on XML**. XML samples ranged from 2,020–2,279 ms for the baseline and 2,093–2,184 ms for the candidate. These overlapping five-sample ranges do not establish either a systematic regression or an improvement; the recorded slowdown remains a pre-1.0 performance follow-up. There is no blanket “faster” claim.

The XML fixture contains 2,048 fully materialized, valid 1 MiB XML files plus a small .NET project. It is not sparse storage or metadata-only simulation. The candidate binary grew from 20,736,626 to 21,007,970 bytes, about 1.3%.

| Candidate workflow | Small mixed project | XML plus tiny project |
| --- | ---: | ---: |
| Discovery + offline plan + declarations, total wall | 101.88 ms | 164.05 ms |
| Unconditional all + declarations + metrics, wall | 27.83 ms | 2,365.61 ms |
| Staged maximum process peak RSS | 34.67 MiB | 35.12 MiB |
| Unconditional peak RSS | 38.72 MiB | 71.52 MiB |

These workflows produce different evidence. The staged lane performs explicit caller-selected declaration inspection; it does not execute the plan. It omits the broader language/metrics work, so its lower cost on XML is not an equivalent-output speedup. On the five-file, 265-byte small fixture, extra process startup and report handling make staging about 3.7 times slower. The planner therefore offers inspectable choices, not an automatic claim that a first pass always saves time.

On that same small fixture, declarations took 20.82 ms and environment analysis took 20.58 ms. Their RSS medians were 26.75 and 27.11 MiB. The wall difference is too small for a speed claim; environment analysis adds qualified evidence with little measured incremental cost in this case. It may cost more on other project/configuration populations.

## Review limits

Environment evidence is file-level: declaration readers do not provide precise spans or raw-content digests. .NET invocation starts are modeled from project roots in the CLI; explicit starts exist only in the Go API. Installed SDK selection and build success are not resolved. A narrow numeric Python constraint subset is supported; other version grammars and conditions remain qualified.

The capability descriptor covers eight planner-supported modules, not the entire CLI. Plans never execute, probe tools or reopen source roots. Environment and explanation comparison remain explicitly unsupported. Existing focused populations and availability observations are compared only under compatible policy and coverage.

These receipts demonstrate the named cases and workloads, not exhaustive compatibility, all build-system semantics, or universal performance. These original results predate the independent review fixes. Follow-up validation is recorded below; another review remains the gate before merge and release.

The receipt-integrity check does not replay the scans or prove that recorded outputs came from execution. Fresh behavioral reproduction uses the broad and targeted drivers; see their [baseline download instructions](../../tests/context_v080/README.md#reproducing-the-retained-macos-baseline). The retained results describe their original source commit, not subsequent review fixes.
