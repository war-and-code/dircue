# dircue 1.4.0

Dircue 1.4.0 adds an optional repository assessment and extends lockfile analysis with npm workspace-lock ownership. The assessment works without Git or Syft and leaves policy decisions to the caller.

```sh
dircue analyze assessment --source directory --json /content
# Equivalent opt-in on the existing aggregate command:
dircue analyze all --assessment --source directory --json /content
```

The assessment component reports selected file and logical-byte totals (including Linguist-vendored subsets), filename-selected manifest counts by ecosystem and kind, parsed project roots and their path roles, workspace membership, local project references, and npm/NuGet lockfile associations with per-role and outcome-reason detail. Each metric states its population and completeness; bounded example lists are separate from exact aggregate counts. Unparsed manifests, unsupported ecosystems, unknown associations, and parser limits remain visible.

Virtual workspace roots (`go.work`, a workspace-only Cargo manifest, a uv workspace without a project table) and configuration, solution, annotation, and tool-settings records are excluded from the project count. Selected `pnpm-workspace.yaml`, `lerna.json`, and `rush.json` files are recognized but not parsed; their presence makes workspace membership and local dependency counts lower bounds.

The new `--npm-workspace-locks` flag on `analyze lockfiles` and `analyze all --lockfiles` applies npm's workspace-root selection: the nearest ancestor whose `workspaces` list includes the project owns its lockfile; ancestors that do not list the project are skipped. Each member is compared against its own entry in that lock. Assessment always applies this semantics. Without the flag an ancestor lockfile still leaves ownership indeterminate. In both modes, projects governed by Yarn, pnpm, Bun, or Rush files, or by a non-npm `packageManager`, are now `unsupported` or `indeterminate` rather than `missing` (a project's own non-npm `packageManager` applies even beside its own npm lockfile), npm projects whose dependency fields cannot be read are `indeterminate` rather than `not_applicable`, and `.fsproj` and `.vbproj` projects receive NuGet lockfile contexts alongside `.csproj` projects.

An existing Syft report can enrich the same assessment invocation through `--syft-report`. It is imported through the existing package-evidence module and cannot establish native manifest counts, project relationships, lockfile ownership, or completeness.

Npm manifests with a leading UTF-8 byte-order mark now parse successfully. MSBuild `Update` items amend existing items rather than declare packages; shared or imported inputs still leave package absence unknown. Empty Python build-system tables also remain distinguishable from tool-only configuration.

Profiles containing assessment use aggregate schema `1.9.0`; the component starts at version `1.0.0`. Help, the offline guide, schema exports, saved-profile comparison, and inert follow-up planning support the new module. Legacy language output, default `analyze all`, and map semantics are unchanged; [compatibility notes](https://github.com/war-and-code/dircue/blob/v1.4.0/docs/COMPATIBILITY.md) list the refinements to default lockfile outcomes.

See [repository measurements](https://github.com/war-and-code/dircue/blob/v1.4.0/docs/ASSESSMENT.md) and [lockfile observations](https://github.com/war-and-code/dircue/blob/v1.4.0/docs/LOCKFILES.md) for definitions, supported populations, reason codes, and limits.
