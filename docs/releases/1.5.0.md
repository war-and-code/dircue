# dircue 1.5.0

Dircue 1.5.0 expands repository assessment with explicit project groups, local dependency structure, and static entry points. It keeps exact selected file and byte totals separate from what the available declarations can establish. Policy decisions remain with the caller.

```sh
dircue analyze all --assessment --source directory --json /content
```

The optional assessment reports filename candidates, parsed projects, and distinct roots by ecosystem and path role. Supported workspace and solution declarations retain their member counts, unresolved references, and coverage. Definite local dependency edges form an observed connected-project graph; directory layout and matching package names do not establish independent applications or deployable services. Dependency scopes are not conditions, a Maven parent must match the coordinates the child declares, and .NET assembly-name references are counted separately in `connected_groups_with_qualified`. Each graph metric says whether it is complete, a lower bound, an upper bound, or observed only.

Manifest interfaces and deployment declarations add entry-point names and supported project associations to the same invocation. Only buildable, runnable, or deployable declarations are listed; CI workflows and supporting resources are counted by kind instead. Distinct declarations, project associations, and retained/omitted rows have separate totals, so an unassociated Dockerfile does not count as a project association. Script bodies are omitted, nothing is executed, and coverage discloses that source-code entry-point inspection did not run. The catalog covers the existing declaration/deployment adapters rather than treating every language as equally understood.

NuGet contexts now separate candidate lockfile presence, ownership, and the result of the named direct-package-presence check. A static model follows the supported subset of shared props, the project body, shared targets, and confined imports in MSBuild order. Supported literal custom lock paths, harmless shared inputs, version-only central package declarations, and confined imports can reduce uncertainty. Conditions, SDK imports outside the model, dynamic expressions, shared package items, and collisions remain explicit, and each one names the file responsible. This does not run MSBuild, resolve package versions, or verify locked restore.

Assessment uses component version `1.1.0` and aggregate schema `1.10.0`; lockfile observations use provider `1.1.0` and the deployable observer advances to `1.3.0`. Current readers also accept the earlier forms. [Compatibility notes](https://github.com/war-and-code/dircue/blob/v1.5.0/docs/COMPATIBILITY.md) list intentional changes to lockfile and map output. Legacy language commands and default aggregate analysis remain unchanged.

The test additions include hand-labeled mixed-ecosystem trees, exact-count checks under evidence limits, attribution counterexamples, and optional .NET SDK queries restricted to synthetic fixtures. Runtime analysis stays offline and works without Git, Syft, a .NET SDK, or package-manager execution. See [repository measurements](https://github.com/war-and-code/dircue/blob/v1.5.0/docs/ASSESSMENT.md) and [lockfile observations](https://github.com/war-and-code/dircue/blob/v1.5.0/docs/LOCKFILES.md) for supported evidence and limits.
