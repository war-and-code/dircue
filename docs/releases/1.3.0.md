# dircue 1.3.0

Draft release notes for review; this version has not been released.

Dircue 1.3.0 expands the offline directory map with declared project and launch relationships: Gradle settings workspaces, root Procfile processes, and declaration-backed .NET Aspire projects.

- Literal Gradle settings includes become partial workspace membership when a selected Gradle project can be identified uniquely. Settings-only roots remain distinct from buildable project declarations; dynamic and ambiguous paths stay qualified.
- Root Procfile processes retain names and supported literal source targets while withholding commands, arguments and environment values. A process links to a project only when both its selected entry file and nearest compatible project are unique.
- Aspire run links now require supported direct C# syntax, an AppHost SDK declaration and a matching unconditional selected project reference. This replaces earlier name-only heuristics. Uncertain forms remain unlinked.
- Launch attribution rejects misleading whitespace, changed search paths, builder shadowing and project-wide aliases. Incomplete Aspire context produces an explicit coverage reason and withholds the declaration; the observer does not perform general C# symbol resolution or evaluate imported MSBuild files.
- `map settings --json` exposes the new observer limits. The deployable observer advances to 1.2.0; the map keeps its existing schema and relationship types. The language-only path and default aggregate analysis are unchanged.
- PyPI installation smokes wait for all seven verified wheels to appear in both public catalogs and the generated `uv` lock. Propagation and transport failures have bounded retries; mismatched artifacts fail immediately.
- Regression checks now cover topology destinations, source evidence, partial coverage and canonical graph identities. Parser benchmarks and a paired whole-CLI harness support later optimization work: differing answers prevent timing comparisons. Linux CI runs the benchmark assertions, actual CLI comparison and focused attribution mutation checks. The [benchmark guide](https://github.com/war-and-code/dircue/blob/main/docs/BENCHMARKS.md) explains their scope and measurement limits.

These are source observations, not proof that a project builds or a process runs. The observers do not execute inspected code, package managers or network requests. See the [map guide](https://github.com/war-and-code/dircue/blob/main/docs/MAP.md) and [compatibility policy](https://github.com/war-and-code/dircue/blob/main/docs/COMPATIBILITY.md) for supported forms and limits.
