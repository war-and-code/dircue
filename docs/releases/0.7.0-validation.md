# 0.7.0 candidate evidence

0.7.0 adds opt-in project focus, source-availability observations, and targeted explanations. The candidate keeps existing commands as regression gates; it does not expand the language catalog or structural grammar set.

## Candidate identity

The measured core has SHA256 `758664d3ed32a66db77b2f96ba1f1b2f62863b1ffd209beb2843de3960577555`, built with Go 1.26.6 on Darwin ARM64, cgo disabled, and release optimization flags. It reports version 0.7.0 for validation; this is not evidence of a published release.

The [build receipt](../../tests/focus_v070/results/build.json) records the command, Go build information, base commit/tree, dirty-worktree identity, and 347 local compilation input hashes. Implementation was uncommitted at measurement time. Those hashes bind the measured code independently of later documentation and evidence commits; the final worktree was checked against every recorded input.

The reference is the verified Darwin ARM64 **0.6.1 release binary**, SHA256 `2cfe46f0467a422124a94ec1931cc91ccd92be95fa1d61f6ff043ba260f29145`. Native structural checks use the verified released worker, SHA256 `73cc5ed95a5b81dcc97c91d57b99a0db4e71ff45bdb74ce8a8193e60e3d53740`.

## Compatibility and new behavior

- **278/278 inherited cases** matched raw stdout, stderr, and process exit status against 0.6.1, with no output normalization. The matrix includes legacy selection, projects, native structure, earlier optional modules, declarations, and comparison. Help/version additions are outside that preservation matrix. [Captures and fixture identities](../../tests/focus_v070/results/broad-compatibility.json.gz).
- **12/12 additional inherited command cases** matched on authored .NET and Python/uv fixtures, including formats and native hotspots. Both focus cases passed independently specified primary/context/related expectations. Focused scc file records match the same files in a full-root run, and totals recompute from those records. [Focus conformance receipt](../../tests/focus_v070/results/conformance-native.json.gz).
- Package and scanner tests cover ambiguous ownership, nested malformed/unsupported/nonregular manifests, shared configuration, declared workspace membership, cycles, cancellation, read failures, selected revisions, dirty directories, output/work limits, and presentation trimming that preserves the execution population.
- Explanation tests compare traces with actual scanner decisions, check attribute provenance and bounded facts, reject conflicting retained evidence, and verify repeated saved-report queries bind to the newly supplied bytes without reopening their source.
- Availability tests separate pointer metadata, attributes, Gitlinks, submodule declarations and checkout sparsity. Oversized parser inputs retain bounded lexical evidence; reverse-order cases above the cap verify that policy. Unsupported or incomplete metadata stays qualified.
- Aggregate schema 1.6.0 is confined to the new modes. Validation rejects mixed repository/focused metric populations and mismatched source/scope identities. Existing comparison rejects 1.6.0 explicitly; retained explanations accept it through bounded schema validation.

The [receipt verifier](../../tests/focus_v070/verify.py) recomputes captures, coverage, per-file equivalence, derived totals and timing summaries. Seven adversarial harness tests include missing cases, altered metric counters with recomputed capture hashes, and an incorrect executable digest hidden elsewhere in a build record. Receipts are reproducibility evidence, not signed attestations or universal compatibility proofs.

## Whole-workflow measurements

Measurements used one macOS ARM64 host, eight scanner workers, one warmup and five measured fresh processes per lane in alternating order. Local builds/tests were paused. Filesystem caches were warm; other desktop services remained active. Times include startup, inventory traversal, declaration planning, requested metrics, and JSON output. Peak RSS is measured by the operating system.

The public ASP.NET Core checkout was clean at `7387de91234d3ef751fa50b3d1bfede4130213ff`. Its measured directory contained **16,515 regular files / 173,287,602 bytes**. The selected Antiforgery project population contained **32 files / 91,464 bytes**. Full-content input manifests were checked before and after measurement.

| ASP.NET Core directory workflow | Median ms | Median peak RSS MiB |
| --- | ---: | ---: |
| 0.6.1 language profiling | 1,238.86 | 61.42 |
| Candidate language profiling | 1,263.46 | 62.22 |
| Candidate focus plan | 650.63 | 52.91 |
| Candidate focus plus metrics | 658.59 | 54.25 |
| Candidate full-root metrics | 1,255.38 | 71.62 |

Focused metrics took **47.54% less time** than full-root metrics on this input. The final ordinary-language median was **1.99% higher** than 0.6.1; small differences varied in exploratory runs and do not establish a default-path speedup or a universal zero-overhead claim. The ASP.NET focus report remains **partial**, with one incomplete-declarations omission. This is useful qualified selection, not proof of complete build-context resolution.

The authored Python/uv fixture contains nine files / 402 bytes. Candidate language profiling took 20.64 ms versus 20.76 ms for 0.6.1; focused metrics took 21.61 ms versus 22.18 ms for full-root metrics. These small differences are timing noise, not a meaningful speed advantage. Its focus is partial because of an intentional nested unsupported Cargo ownership boundary.

[ASP.NET Core samples and qualifications](../../tests/focus_v070/results/performance-aspnetcore.json.gz), [Python/uv samples](../../tests/focus_v070/results/performance-uv.json.gz), and the [reproduction instructions](../../tests/focus_v070/README.md) retain the measurement details. Different projects and hosts can produce different tradeoffs.

## Availability and explanation costs

A separate quiet measurement window on the same ASP.NET Core input used one warmup and five fresh processes per lane. These commands answer different questions, so their times are **not equivalent-work speedups**:

| Requested analysis | Median ms | Median peak RSS MiB |
| --- | ---: | ---: |
| Language profiling | 1,241.97 | 62.28 |
| Availability | 1,835.49 | 43.97 |
| One fresh file explanation | 534.56 | 31.64 |
| Explanation from a saved report | 57.10 | 33.28 |

Availability inspected 16,384 prefixes, reading 13,443,752 bytes, and explicitly omitted 131 pointer candidates at its admission limit. Its report was partial. This content inspection is more expensive than language profiling on this input and stays opt-in. The fresh explanation still pays for contextual metadata traversal; the saved query validates retained report bytes instead of rescanning source.

[Recorded samples, commands and coverage](../../tests/performance/v070_targeted/results.json) and the [measurement script](../../tests/performance/v070_targeted/measure.py) provide reproduction details. An earlier exploratory cost run overlapped a fuzz campaign and is not used for this table.

## Release gates

Local validation passed: `go vet ./...`, the full `go test -race ./...` suite, 67 Python release-helper tests (two explicit execution opt-ins skipped), seven adversarial harness tests, 12 workflow-expression tests, Actionlint, and the compiled-core targeted smoke helper. Logs and the smoke receipt are retained in the [results directory](../../tests/focus_v070/results/).

The final bounded availability-parser fuzz campaign passed **1,482,695 executions in 31 seconds**, with four workers. It checks deterministic results, output caps, truncated inputs, and index payloads both with and without repaired checksums. [Source hashes and command](../../tests/focus_v070/results/availability-fuzz.json), [log](../../tests/focus_v070/results/availability-fuzz.log). This is a bounded campaign, not exhaustive parser verification. An earlier four-million-execution run preceded the final lexical-retention fix and is not substituted for this result.

 Full native-platform, Linguist and scc checks run on the ready pull request. Targeted packaged-core smoke checks exercise focus, availability and fresh/retained explanations on each of the five native distribution platforms; release assembly requires their matching receipts. Successful compilation alone is not a native execution claim.

The pull request and its exact-head checks are the source for hosted validation status. No tag or published release is implied by this candidate evidence document.
