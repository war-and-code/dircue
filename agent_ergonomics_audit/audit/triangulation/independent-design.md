# Independent review of proposed additive discovery direction

This review follows, and does not replace, independent-findings.md. Direction reviewed: capabilities --cli --json; capabilities --schema NAME --json; capabilities --guide; stderr-only corrective hints; inert JSON argv in plain plans. Overall: appropriate additive scope, provided the following contracts are explicit.

1. Keep bare capabilities and capabilities --json behavior and bytes unchanged. Put new modes behind mutually exclusive local flags. Do not add new root command names: any new root verb reserves another formerly valid bare directory name. Keep -- delimiter and ./ routing unchanged, including when flags precede the delimiter.
2. Derive structural metadata (command path, help, flags, defaults, shorthand, required args) from the actual Cobra tree, but attach explicit semantic metadata. Inheritance does not mean applicability: capabilities, plan, compare reject nine scan flags; explain has conditional source/report requirements. Filtering only by flag registration gives a false contract. Sort command/flag descriptors deterministically and do not trigger scanning, worker probing, or schema compilation to build them.
3. Define command counting precisely. Existing tree has 18 analyze children (17 constructed in the loop plus explain), analyze itself, root, compare, plan, capabilities, and Cobra's help. Exclude or label command groups and generated help rather than advertising an unexplained command total. Ensure generated help initialization does not make descriptor contents depend on prior calls.
4. Output families must match emitters: root/analyze languages use the Linguist map, frameworks/ecosystems use finding arrays, most analyze commands emit the aggregate profile despite module-specific names, explain emits its own shape, compare/plan/capabilities are distinct. Module subschemas such as declarations are not standalone output schemas for analyze declarations. A schema index should distinguish complete outputs from component schemas.
5. Self-contained export must preserve reference base identity. All 13 shipped schema files currently lack $id. profile references seven filenames, and component schemas have local #/$defs references. Simply nesting components under the exported root's $defs can redirect those local refs to the wrong document. A resource bundle with explicit canonical retrieval URIs, or a standards-compliant compound schema whose component $id values preserve base identity, is safer. If refs are rewritten, rewrite both inter-resource and local refs completely. Offline validation must disable network loaders; $schema names a dialect, not an instruction to fetch it. Verify positive and negative instances against both original resources and exports.
6. New CLI descriptor and guide JSON need their own stable kinds/versions and validation contracts. Exporting schemas is not the same as offering a report-validation command. State clearly whether the installed CLI validates caller files, exports schemas for external validation, or only self-validates capability metadata. Avoid implying that profile validation covers planner/capability JSON; schema.ValidateProfile currently validates profile only.
7. Environment documentation should be static names and semantics, not current values, cwd, home, Git configuration, repository paths, or executable locations. DIRCUE_STRUCTURAL_WORKER found in source is test-only; production structure requires the flag. Do not infer supported configuration from test getenv calls or inherited Go runtime controls. Distinguish supported app configuration from optional runtime tuning.
8. Guide should present metadata-only discovery, light content profiling, explicit source selection, metrics versus structure, saved-report selection, and legacy/output-schema differences. Light does not mean metadata-only: analyze all classifies language content. Document success-with-partial-coverage and comparison-with-differences as exit 0; failures stay 1. No automatic execution or external fetching.
9. Suggestions should be limited to actual flags on the selected command, handle transposition --jsno, and never read input path contents. Unknown root operands may be intended filesystem paths, so do not silently reinterpret them as commands. Escape control characters in echoed user input. Keep original failure, stderr-only diagnostics, and exact legacy JSON success output.
10. Plain plan argv should use JSON encoding of argument arrays with explicit inert-template labeling and existing executable:false/source-placeholder/revalidation semantics. Show unresolved inputs and source boundary limitations. Do not shell-join or substitute an untrusted declared root, and do not weaken unknown-source status to make commands copyable.

Supplemental runtime probes confirm the two help/plan issues: plain plan currently prints only decisions, not step argv; capabilities --source directory --json exits 1 despite advertising --source in help. Transcripts 09 and 10 are outside the canonical-task counts.


## Scoring caveats

Root/analyze languages have a separate single-file JSON shape (internal/cli/file.go: fileOutput/runFile), not the languages-directory schema. A new schema catalog must explicitly disclose missing single-file schema coverage. Schema validation is not a general JSON promise: reject nonstandard NaN/Infinity inputs explicitly and do not infer that a schema-export command itself validates user files. Existing strengths receive evidence-based scores; only rubric-defined inapplicable dimensions receive 1000 as n/a.
